# M10 — The first checker, written from the specification alone

**Depends on:** [M8](m8.md).
**Discharges:** [M6](m6.md)'s recorded weakest link — "a fixture written by the
same person who wrote the check tests the check against its author's
understanding of it ... the real test is the first independent checker".

Zero implementations of this specification exist. Every claim the catalog makes
about being implementable, language-neutral, and precise enough to build from is
untested. This is the unit that converts the largest open risk in the repository
into either evidence or a list of defects.

**The independence here is partial, and the record says so on its face.** Phase
one was written by the owner with an Opus 5 instance co-authoring. The
implementer is a different Opus 5 instance that did not write any of it and has
no phase-one context — a different session and a different reader, but not a
different lineage. See
[decisions.md](../decisions.md#the-first-checker-is-whippys-and-its-independence-is-partial).

## Done means

- A checker covering all five modules exists and reproduces every expectation in
  [M8](m8.md)'s files across all 33 fixture trees.
- **It does not live in this repository.** No runner ships here — see
  [decisions.md](../decisions.md#there-is-no-runner-and-that-is-the-largest-single-decision-here).
  A checker committed alongside the specification becomes the reference
  implementation whatever its README says, and the second implementer then
  writes against it rather than against the spec. It lives in a repository of
  its own, named before the unit starts.
- Its only inputs are this repository's published files. No phase-one
  conversation, no work-in-progress branch, and no access to the author's
  intent beyond what is committed.
- **The author does not answer questions about what a check means.** Every
  question the implementer has to ask is the deliverable, not an obstacle to it.
  This rule is enforced by the owner declining, and it cannot be reinstated
  after it has been broken once.
- Each such question is recorded as an ambiguity **before** the implementer
  resolves it, with the check id, what was unclear, the readings available, the
  one taken, and how confident that choice was. Recording it afterwards records
  a conclusion; recording it first records the fork.
- Each recorded ambiguity is then resolved as exactly one of: a new fixture that
  pins the boundary, an obligation reworded, or a decline with reasoning. This
  is [SPEC.md](../../../SPEC.md) "Ambiguity is a missing fixture" run for the
  first time, and an empty list is a signal the independence rule leaked rather
  than that the spec was clear.
- The ambiguity list is written up under the `investigations` role, and
  [strucgu.yaml](../../../strucgu.yaml) maps that role instead of leaving it
  unmapped. The four `IN-*` checks stop reporting `skip` because a real
  investigation now exists — not because one was invented to exercise them. See
  [self-walk.md](../self-walk.md), where those four skips are described as the
  point of the walk.
- Deliberately not done: no second implementation. Two checkers disagreeing is
  the sharper test and it costs a second independent party; one is what this
  unit buys, and what it does not prove is stated in the record rather than
  implied away.

## Risks

**Shared lineage is the risk that cannot be measured from inside.** A reader
from the same model family may reconstruct the co-author's reading of an
ambiguous check without ever noticing there was a fork in the road — and the
output looks identical to a spec that was simply clear. The confidence field
above is the only instrument against it: an ambiguity resolved correctly at low
confidence is a coin-flip that landed, and counting those separately is the
difference between "the spec was precise" and "two instances of one model guessed
alike".

Independence is otherwise fragile in the ordinary way. If the implementer asks
and is answered, this unit produces dogfood with more steps, and the failure
would not be visible in the output, because a checker built with help still
passes the fixtures. Which is why a thin ambiguity list must be read as
suspicious rather than as good news.

Reproducing the expectations proves the checker agrees with the fixtures, which
is a weaker claim than conforming to the specification. The two come apart
exactly where the fixtures under-determine a check — [F2](../findings.md) is
already a known instance — and that gap is what [M11](m11.md) is for. With
[M9](m9.md) deferred, "conforms" means only "reproduced the expectations" for the
duration of this unit, and that reduced meaning should be stated wherever the
result is reported.

This unit has no upper bound on effort. A checker covering five modules and 28
checks is a real project. If it is scoped down, scope it by **module**, not by
check — a checker covering three modules completely tells the truth about those
three, where one covering half of each tells the truth about nothing.
