# M8 — Fixture expectations become machine-comparable

**Depends on:** [M6](m6.md).
**Discharges:** the gap between what `expected.md` says and what a second party
can mechanically check their checker against.

Each module's `fixtures/expected.md` states, in prose and tables, what a correct
checker produces on each tree. Prose is the right form for *why* a fixture
exists and what boundary it pins. It is the wrong form for the one question an
implementer actually has — *did my run match?* — which today can only be
answered by a person reading 33 trees against five documents.

## Done means

- Each module carries a `fixtures/expected.yaml`, beside the prose file it
  restates, in two keyed sections: check results per fixture tree per check id,
  and **judgment entries keyed by their own ids**. Each value is one of the five
  states in [SPEC.md](../../../SPEC.md) "Audit output". Nothing else.
- **Judgment entries are keyed separately because they are not checks.**
  [SPEC.md](../../../SPEC.md) "Judgment entries" gives them their own ids and
  requires one `judgment` line per entry whether or not anyone is available to
  judge it. A file keyed only by check id cannot express that, and
  [M10](m10.md)'s conformance test would then be silent on the one output
  channel that stops a mechanical run from looking complete — the 17 lines
  [self-walk.md](../self-walk.md) counts.
- It declares its own schema identifier on the first line, the way the adoption
  record does. A data file with no version is one a consumer cannot pin, and
  every other file here that crosses a boundary carries one.
- **The identifier is defined in [SPEC.md](../../../SPEC.md), not only used
  here.** `strucgu/module@1` and `strucgu/adoption@1` are defined there; a third
  that appears only inside a fixture directory is a pin to nothing.
- **[SPEC.md](../../../SPEC.md) changes, and this unit names how.** "What a
  module is" says a module directory contains *exactly* the listed files, and
  its `fixtures/` row lists a `satisfies/` tree, one `violates-<CHECK-ID>/` tree
  per check, and `expected.md`. Both sentences become false when this file
  lands. They are edited by this unit, and the bump is **minor** under
  [SPEC.md](../../../SPEC.md) "Versioning" — nothing a previously clean adopter
  newly sees — with each module changelog saying so in the fixed sentence.
- **Finding text is deliberately excluded.** An expectation file that pins the
  wording of a finding makes one implementation's phrasing normative, which is
  the thing [decisions.md](../decisions.md) refused when it refused a runner.
  What a finding must *carry* — a location and evidence — is already in the
  spec; how it reads is the implementer's.
- `expected.md` stays, stays prose, and stays the statement of intent. The two
  files must agree; where they disagree that is a bug to report, not a
  precedence order to apply — the same rule [README.md](README.md) already
  states for `module.md` and `module.yaml`.
- The state vocabulary in the file is the spec's five states verbatim. A sixth
  value appearing anywhere is a specification change and cannot enter through a
  fixture.
- Every tree that exists on disk appears in its module's file, and every entry
  in the file names a tree that exists. A missing row and a passing check are
  indistinguishable otherwise.
- Deliberately not done: no schema file, no validator, and no tooling to read
  these. The file is data an implementer parses with what they already have.

## Risks

The neutrality rule is under strain and the argument that it is not breached is
in [decisions.md](../decisions.md#fixture-expectations-become-data-and-the-wording-of-a-finding-stays-out-of-them),
not repeated here. If a reviewer disagrees, the disagreement is about the rule's
wording rather than this file.

The second risk is worse and has no clean fix: a machine-readable expectation
file is the closest thing to shipping software that the no-runner decision
permits, and the next request after it will be for a harness that reads it.
[M9](m9.md) was written to guard that line and is now deferred until
[M10](m10.md) has shown where it actually falls. Between this unit and that one
the line is unguarded, and holding it is the owner's judgment rather than a
document's — which is a real cost of the deferral and is recorded here rather
than in the unit that was deferred.
