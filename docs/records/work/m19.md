# M19 — The implementation is pulled up, and the new trees are tested against a wrong checker

**Depends on:** [M17](m17.md) and [M18](m18.md), hard. There is nothing to
re-measure until the trees they add exist.
**Discharges:** `F14` in [findings.md](../findings.md), and the claim
[M17](m17.md) cannot make about itself.

[strucgu-check](https://github.com/DevOfPie/strucgu-check) reproduces the catalog
at `0.2.0` and is five rows behind at `0.3.0`. Pulling it up closes `F14`. The
reason this unit exists is the second half: a fixture written by the party that
wrote the implementation may pin what that implementation happens to do, and the
only way to tell is to break the implementation on purpose and see whether the new
trees notice.

## Done means

- The checker reproduces every row of every module's `expected.yaml` at the
  versions this phase ships, including the sections [M18](m18.md) adds, and the
  run is recorded with its counts.
- **The deliberate-breakage measurement is re-run against the new fixture set.**
  Phase two broke the checker nine ways, one stated rule at a time, and **five of
  nine still produced a clean run**. The same nine breakages are re-applied, plus
  one per behaviour [M17](m17.md) newly pinned, and the unit records how many go
  unnoticed now. A number that has not improved is the unit's most useful possible
  output.
- **Whether the ambiguity list grew is answered.** A moved contract can create
  ambiguities where none existed. The implementer records any new one before
  resolving it, in the form
  [investigations/0001](../investigations/0001-what-the-specification-does-not-determine.md)
  established, and each becomes a specification finding rather than a private
  reading.
- The checker is run over **this** repository as well as over the fixtures, and
  any result that moved since the `0.2.0` walk is explained rather than reported.
- No register of implementations is created, no list of conforming checkers is
  published, and nothing is added anywhere for an implementer to submit a claim
  to. [conformance.md](../../conformance.md) refuses all three and the refusal is
  unaffected by this repository happening to own the implementation it is pulling
  up.
- The independence limit is restated where the results are: this implementer
  shares a model lineage with phase one's co-author, so the measurement bounds the
  fixtures rather than demonstrating that an unrelated implementer would pass.
- `F14` moves to *Closed* with its disposition.

## Risks

**The unit can flatter itself and it will not look like it is doing so.** The same
party writes the trees and fixes the checker, so a breakage the trees miss can be
quietly re-classified as not-a-breakage. The defence is that the nine breakages
from phase two are already written down and are re-applied verbatim rather than
re-derived.

Owning the only implementation also makes `F14` cheap to close and makes the
question `F14` actually asked — *has anyone implemented this, and does their run
still match?* — cheaper to keep avoiding. Closing the row does not answer it.
[conformance.md](../../conformance.md) already refuses the register that would,
and the honest statement is that propagation stays pull-only and this repository
pulled its own.
