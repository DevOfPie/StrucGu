# M20 — The adoption path is ready for a repository this one does not control

**Depends on:** [M16](m16.md), [M17](m17.md), [M18](m18.md) and [M19](m19.md),
all hard. The guide describes a schema those units change and a checker they move.
**Discharges:** the readiness [M21](m21.md) releases, and nothing in the queue.

Every adoption this catalog has seen was performed by somebody who could ask the
author. This repository adopted itself; the second repository's adoption was run
from inside this phase's predecessor. **LinkCtrl will transition in its own
workflow, after this phase lands**, which means the guide has to answer its
questions before anyone is there to be asked.

This unit does not write an adoption record anywhere. It makes the path
walkable and finds out where it is not.

## Why LinkCtrl is the worked example, and why that is not adoption

It is public, so every question can be quoted rather than redacted. It is the
repository whose shape most stresses the guide — it keeps more record types than
the catalog has roles for, and it separates records this repository conflates. And
because it is the repository these conventions were extracted from, using it as an
example carries no risk of the example being unrepresentative in the direction that
matters: if the guide cannot answer *this* tree, it cannot answer any.

**None of that makes it a data point.** [README.md](../../../README.md) says two
adoptions, both adjacent to the author, and this unit does not move that number —
no adoption happens here. When LinkCtrl transitions later, it will be a third and
the most adjacent one available, and whatever record it produces then has to say
so.

## Done means

- **[adopting.md](../../adopting.md) is walked literally against LinkCtrl's public
  tree**, and every question it fails to answer is either answered in the guide or
  filed. The walk is recorded with what was asked, not only what was fixed.
- **The more-than-one-process-document case is answered.** `triage_doc` is a
  single role. LinkCtrl's process is three documents with a stated precedence
  between them — gates, sequence, and intake. The guide says what an adopter in
  that position maps, and what the unmapped ones' invisibility costs. Stated by
  shape, not by filename: the answer has to fit a repository nobody here has read.
- **The record-no-role-reaches case is answered.** LinkCtrl's scope contract is a
  file no role can reach, because `unit_index` is the index rather than the scope
  contract. The guide today has no instruction for *I keep a record this catalog
  cannot see*, and the answer is that it stays unmapped and that this is expected
  rather than a defect in the adopter. **This does not close `F9`** and the guide
  says which finding it is living with.
- **Choosing `effective_from` against real history is answered.** This repository's
  own case was free — its first commit was the effective date, and there was no
  history to exclude. An adopter with years of it, and with removals in it, needs a
  rule. The guide has none today.
- **The unmapped list is produced and filed.** Every record type LinkCtrl keeps
  that no role reaches is named in [findings.md](../findings.md), with what it is
  for. None is fixed here: growing the catalog is out of scope for this phase.
- **A worked example ships or it does not, and either way it is labelled.** If the
  guide carries an example role mapping, it is marked as an example rather than as
  a record, and it pins no versions this repository has not released.
- Nothing is committed to LinkCtrl, and nothing is built for LinkCtrl to run this
  on a schedule. The transition is the adopter's work in the adopter's process.

## Risks

**A guide written against one known repository fits that repository.** The
defence is stated in every bullet above: each question is answered in terms of a
*shape* — more than one process document, a record no role reaches, history that
predates adoption — and never in terms of LinkCtrl's filenames. A guide that names
them has documented one adoption instead of the path.

**Readiness is unfalsifiable until someone adopts.** This unit can declare the
path walkable and be wrong, and nothing here would catch it. The honest claim is
narrower than "ready": every question that could be found has an answer. The test
is LinkCtrl's transition, which happens outside this phase and may well produce
findings — and that is the expected outcome rather than a failure of this unit.

**The temptation is to pre-solve `F9`.** A sixth role would make the unreachable
scope contract reachable and would be a catalog change smuggled in under a
documentation unit. The guide documents the gap; it does not close it.
